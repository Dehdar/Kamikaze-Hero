# Project structure

This guide explains how Kamikaze Hero is put together, so you can find your
way around before changing anything. It describes the shape of the project
rather than every file; when in doubt, the scripts in `Assets/Scripts` are
short and are the source of truth.

## Top-level layout

```
Kamikaze-Hero/
├── Assets/            Everything that ends up in the game
├── Packages/          Unity package manifest and lock file
├── ProjectSettings/   Unity project settings (build targets, tags, input…)
├── docs/              Developer documentation (this file)
├── README.md          What the project is and how to open it
├── CHANGELOG.md       History of features added and removed
├── LICENSE            MIT license for the project
└── CREDITS.md         Authors and licenses of third-party content
```

`Library/`, `Temp/`, `Logs/`, `UserSettings/` and build output are generated by
Unity and ignored by git.

## Assets

| Folder | Contents |
| --- | --- |
| `Scene/` | The three scenes and their lighting settings |
| `Scripts/` | All game code (plain `MonoBehaviour` scripts, no assembly definitions) |
| `Prefabs/` | The player, enemies, bullets, explosions and the kamikaze weapon |
| `Prefabs/Dependencies/` | 3D models used by the prefabs, plus the third-party fire-effects scripts |
| `Animation/` | Animator controllers and clips for the menu, wave banner and game-over screen |
| `Materials/` | Materials and one custom additive shader |
| `Textures/` | Textures, UI images and particle sprite sheets |
| `Sounds/` | Music and sound effects |
| `Fonts/` | The UI font |

Third-party content is listed in [CREDITS.md](../CREDITS.md).

## Scenes

The build contains three scenes, in this order (see **File > Build Profiles**):

1. **Menu** – title screen with Start, About and Exit. This is the entry point.
2. **Game** – the actual game.
3. **About** – a note from Ali and the credits, with a back arrow to the menu.

Scenes are switched by name with `SceneManager.LoadScene`, so renaming a scene
means updating the strings in the menu code.

## How a game session flows

1. **Menu.** The menu controller handles the buttons. Starting a game loads the
   Game scene (and every third game shows an interstitial ad through the ads
   manager). A music object is created once and survives scene changes.
2. **Game starts.** The spawn manager shows the "WAVE n/20" banner and starts a
   coroutine that spawns enemies wave by wave. The number of enemies, which
   enemy types can appear, and the spawn delay all depend on the wave number.
3. **Player.** The player prefab carries the movement script (keyboard in the
   editor, touch drag on Android, clamped to a boundary box) and the attack
   script (three-shot bursts and the kamikaze weapon). On-screen fire and
   kamikaze buttons report their pressed state to these scripts.
4. **Enemies.** Each enemy type has a small movement script: straight missiles,
   guided missiles that track the player's height once past mid-screen, and
   multi-missile formations. A collision script on the enemies handles hits:
   a bullet hit adds score and spawns an explosion, a player hit kills the
   player.
5. **Bookkeeping.** A statistics component counts enemies spawned and missed,
   bursts fired and score. A border trigger at the left edge counts enemies
   that got past. The game manager only tracks whether the player is alive.
6. **Game ends.** When the player dies or wave 20 is cleared, the spawn manager
   fills in the game-over panel (score, kills, accuracy, verdict) and plays the
   end-game animation. Restart reloads the Game scene.

## Scripts by role

Script names may change as the code is cleaned up; the roles stay the same.

| Role | Scripts (current names) |
| --- | --- |
| Menus and scene flow | `MenuController`, `ButtonLoader`, `EmailScript` |
| Game state and scoring | `GameManager`, `SpawnManager`, `Statistics`, `PlayerScore`, `Counter`, `BorderManager` |
| Player | `PlayerMovement`, `PlayerBoundary`, `PlayerAttack`, `FireController`, `KamikazeController`, `WingMovement`, `PropelSpinner` |
| Enemies and projectiles | `MissileForward`, `GuidedMissileForward`, `MultiMissileForward`, `Bullet`, `Impact`, `ExplosionMover` |
| Presentation | `BackgroundMover`, `AudioController` |
| Services | `AdsManager` (Unity Ads 4.x) |

The `Fire*` scripts in `Prefabs/Dependencies` (namespace
`DigitalRuby.PyroParticles`) drive the explosion and fire particle effects.
They are third-party code; see [CREDITS.md](../CREDITS.md).

## Conventions worth knowing

- **Tags are used for lookups.** Scripts find each other with
  `GameObject.FindGameObjectWithTag` (for example `GameManager`, `Player`,
  `Menu`) and tell enemy types apart by tag (`Missile`, `GuidedMissile`,
  `MultiMissile`). If you add a new enemy or rename a tag, check
  **Project Settings > Tags and Layers** and the spawn and collision code.
- **Tuning lives in the Inspector.** Speeds, delays and wave counts are public
  fields set on prefabs and scene objects, not constants in code.
- **Text serialization.** Assets are stored as text (`Force Text`), so scenes
  and prefabs diff and merge reasonably in git. Always commit the `.meta` file
  next to any asset you add, move or rename.

## Packages

`Packages/manifest.json` lists the Unity packages the game depends on, most
notably Unity Ads (`com.unity.ads`) and uGUI (`com.unity.ugui`).
`packages-lock.json` pins exact versions; commit both when you add or update a
package.
